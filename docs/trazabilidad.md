# Trazabilidad de requisitos — Katalyst

Matriz exigida por ESP §14: una fila por cada RF/RNF de la especificación (**76 IDs**, verificado contra
`Especificación_Requerimientos/Especificación_Requerimientos.md`). Estados permitidos: `pendiente`, `validado`,
`diferido`, `bloqueado`. Criterio aplicado (consolidación del 2026-11-06):

- `validado`: implementado y con prueba automatizada que pasa o acta de aceptación local (`docs/aceptacion/*.md`) que lo demuestra.
- `validado (local)`: variante de `validado`; la validación completa requiere además un sistema externo (TestRail real, staging
  DeltaX, AWS, Windows 11, plataforma Git, canal o IA reales). La columna Evidencia indica «Falta: …».
- `bloqueado`: no puede implementarse o validarse por una dependencia externa ausente; se indica el bloqueo.
- `diferido`: solo Debería/Puede excluidos explícitamente (con razón y destino). Hoy ninguno.
- `pendiente`: falta trabajo de código propio; se indica exactamente cuál.

"Base" indica contratos/lógica pura o esquema entregados por el agente de base. Las pruebas citadas viven en
`packages/shared/test/`, `apps/api/test/`, `apps/web/test/`, `apps/recorder/test/` y (prefijo «runner:») `apps/runner/test/`.
Las filas con panel (WEB) se validan contra el contrato de `@katalyst/shared` mediante MSW (D-052); el recorrido del panel
contra la API real no tiene prueba automatizada propia (la API se ejercita por HTTP en `docs/aceptacion/e2e-local.md`).
